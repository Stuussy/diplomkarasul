# 🛠 MVP Execution Plan

## Phase 1 — Critical fixes

### MVP-001

- ID: `MVP-001`
- Название: Восстановить compile-clean frontend
- Описание: Исправить все blocking ошибки из `flutter analyze`, начиная с рассинхрона между `ApiService`, `SessionProvider` и экранами. Убрать отсутствующие методы, несовместимые сигнатуры, несуществующие theme/icon references и ошибки с именованными параметрами.
- Приоритет: High
- Тип: bug
- Ожидаемый результат: `flutter analyze` завершается без ошибок; проект снова можно собирать и запускать.
- Зависимости: нет

### MVP-002

- ID: `MVP-002`
- Название: Починить auth flow на frontend
- Описание: Привести `LoginScreen` и `SessionProvider` к одному контракту. Либо provider бросает исключения, либо UI обрабатывает возвращаемые строки ошибок. Отдельно исправить сломанный вызов `register()` с именованными аргументами и проверить показ ошибок пользователю.
- Приоритет: High
- Тип: bug
- Ожидаемый результат: логин, регистрация и сообщение об ошибке работают предсказуемо.
- Зависимости: `MVP-001`

### MVP-003

- ID: `MVP-003`
- Название: Восстановить пациентский appointment flow
- Описание: Починить связку `HomeScreen`, `AppointmentRequestScreen`, `AppointmentsScreen`, `ProfileScreen` и `ApiService`: запись на приём, список своих записей, QR-подтверждение, профиль/штрафы и смену пароля. Использовать один согласованный контракт имен методов и payload.
- Приоритет: High
- Тип: bug
- Ожидаемый результат: пациент проходит demo-сценарий без ручных заглушек и без падений UI.
- Зависимости: `MVP-001`, `MVP-002`

### MVP-004

- ID: `MVP-004`
- Название: Зафиксировать целевую платформу демо
- Описание: Принять одно решение по платформе защиты. Если нужен Android APK, восстановить Android scaffold. Если защита пойдёт на iOS/web, явно зафиксировать это в README и demo checklist, чтобы не тратить время на лишние платформы.
- Приоритет: High
- Тип: infra
- Ожидаемый результат: понятный и проверяемый demo target без платформенной неопределённости.
- Зависимости: нет

### MVP-005

- ID: `MVP-005`
- Название: Привести ветку к demo-safe состоянию
- Описание: Убрать из рабочей ветки инфраструктурный шум: tracked `backend/node_modules`, случайные platform deletions, смешанные незавершённые изменения. Сформировать чистый baseline для демонстрации и следующих правок.
- Приоритет: High
- Тип: infra
- Ожидаемый результат: чистая, воспроизводимая demo-ветка, в которой понятно, какие изменения относятся к MVP.
- Зависимости: `MVP-004`

### MVP-006

- ID: `MVP-006`
- Название: Проверить backend bootstrap и локальный запуск с нуля
- Описание: Прогнать backend bootstrap как новый разработчик: `npm install`, `.env`, seed/demo data, запуск сервера, запуск тестов. Зафиксировать недостающие шаги и обновить инструкции так, чтобы среда поднималась без догадок.
- Приоритет: High
- Тип: infra
- Ожидаемый результат: локальная среда воспроизводится по инструкции, backend smoke-checks запускаются.
- Зависимости: `MVP-005`

## Phase 2 — MVP completion

### MVP-007

- ID: `MVP-007`
- Название: Провести end-to-end проверку ключевых ролей
- Описание: Пройти реальные сценарии минимум для `patient`, `doctor` и `admin`: логин, запись, подтверждение, отмена/перенос, просмотр медкарты, создание слота, генерация QR, stats/overview. Исправить только те баги, которые ломают демонстрацию.
- Приоритет: High
- Тип: bug
- Ожидаемый результат: есть подтверждённый demo flow по ключевым ролям без “ручного обхода” проблем.
- Зависимости: `MVP-003`, `MVP-006`

### MVP-008

- ID: `MVP-008`
- Название: Довести support и notifications до стабильного demo-сценария
- Описание: Проверить создание обращения, ответ, обновление статуса и чтение уведомлений. Исправить runtime-баги и контрактные несовпадения, если они обнаружатся в ручном проходе.
- Приоритет: Medium
- Тип: bug
- Ожидаемый результат: support flow можно уверенно показать на защите.
- Зависимости: `MVP-007`

### MVP-009

- ID: `MVP-009`
- Название: Упростить или исправить map feature
- Описание: Выбрать один из двух вариантов. Вариант A: сделать экран data-driven от реальных клиник. Вариант B: сократить scope и честно позиционировать экран как внешнюю навигацию к выбранной клинике. Не оставлять текущую полу-статичную реализацию как “готовую карту”.
- Приоритет: Medium
- Тип: feature
- Ожидаемый результат: map feature соответствует реальному поведению продукта и не вводит комиссию в заблуждение.
- Зависимости: `MVP-007`

### MVP-010

- ID: `MVP-010`
- Название: Подготовить demo data и сценарий защиты
- Описание: Подготовить минимальный набор пользователей, клиник, слотов, записей и отзывов для быстрой демонстрации. Если нужно, доработать или добавить безопасный seed script без изменения runtime-поведения.
- Приоритет: High
- Тип: feature
- Ожидаемый результат: проект можно показать с “живыми” данными без ручного ввода всего с нуля.
- Зависимости: `MVP-006`, `MVP-007`

### MVP-011

- ID: `MVP-011`
- Название: Добавить минимальные smoke tests для критичных backend flows
- Описание: Расширить текущий backend harness на самые рискованные сценарии: auth, appointments, reviews, records. Цель не в полном покрытии, а в защите от повторного слома MVP-путей.
- Приоритет: Medium
- Тип: infra
- Ожидаемый результат: ключевые backend-regressions ловятся автоматически локально.
- Зависимости: `MVP-006`

## Phase 3 — Stabilization

### MVP-012

- ID: `MVP-012`
- Название: Разделить backend app и server
- Описание: Вынести создание Express app из `server.js` в отдельный модуль, а `listen()` оставить в thin entrypoint. Это нужно для нормальных integration tests и более контролируемого запуска.
- Приоритет: Medium
- Тип: refactor
- Ожидаемый результат: backend становится удобнее для тестов и дальнейшей поддержки.
- Зависимости: `MVP-011`

### MVP-013

- ID: `MVP-013`
- Название: Централизовать admin clinic-scope и RBAC helper'ы
- Описание: Вынести дублирующийся `getAdminClinicIds` и похожие policy checks в общие backend helpers/services. Не менять поведение ради рефакторинга, а только убрать дублирование, которое уже создаёт риск новых access bugs.
- Приоритет: Medium
- Тип: refactor
- Ожидаемый результат: правила доступа определены в одном месте и легче покрываются тестами.
- Зависимости: `MVP-011`

### MVP-014

- ID: `MVP-014`
- Название: Добавить базовые DB индексы и ограничить тяжёлые списки
- Описание: Создать индексы для hot paths по appointments, notifications, messages, reviews, fines. Для крупных list endpoints добавить хотя бы минимальные ограничения или пагинацию там, где это реально нужно для роста данных.
- Приоритет: Medium
- Тип: refactor
- Ожидаемый результат: проект лучше переносит рост данных и меньше зависит от full scans.
- Зависимости: `MVP-013`

### MVP-015

- ID: `MVP-015`
- Название: Production hardening конфигурации и секретов
- Описание: Отключить опасные bootstrap-механизмы вне initial setup, добавить раннюю проверку обязательных env, зафиксировать правила обращения с OAuth tokens и внешними интеграциями. Не строить “идеальный enterprise”, только закрыть очевидные release-риски.
- Приоритет: Medium
- Тип: infra
- Ожидаемый результат: проект безопаснее и предсказуемее при локальном релизе или пилотном деплое.
- Зависимости: `MVP-006`, `MVP-012`

### MVP-016

- ID: `MVP-016`
- Название: Добавить минимальный CI gate
- Описание: Настроить хотя бы один автоматический pipeline с обязательными шагами: `flutter analyze` и backend tests. Если Flutter tests к этому моменту отсутствуют, не расширять scope, а зафиксировать именно минимальный gate.
- Приоритет: Medium
- Тип: infra
- Ожидаемый результат: каждая следующая правка проходит через базовую автоматическую проверку.
- Зависимости: `MVP-001`, `MVP-011`

### MVP-017

- ID: `MVP-017`
- Название: Снизить стоимость поддержки самых опасных файлов
- Описание: После стабилизации вынести самые болезненные куски из `role_dashboards.dart`, `api_service.dart` и крупных backend routes в отдельные модули по зонам ответственности. Делать это только после фикса MVP, чтобы не сорвать сроки диплома.
- Приоритет: Low
- Тип: refactor
- Ожидаемый результат: кодовая база становится проще для сопровождения без большого “архитектурного ремонта”.
- Зависимости: `MVP-007`, `MVP-013`
